# PromptDeck 메인페이지 점검 및 개선 방향

점검일: 2026-09-05 (KST)

## 1. 판단

현재 메인은 시각적 일관성과 서비스 원칙 전달은 양호하지만, 방문자가 원하는 도구를 선택하기까지 설명이 길다. 개선 목표는 **만들 결과물을 빠르게 선택하고 해당 작업 화면으로 바로 진입하는 메인페이지**다.

브랜드 색상과 차분한 화면은 유지한다. 설명의 순서와 분량, 작업 진입 동선을 우선 개선한다.

## 2. 점검 범위와 확인 수준

- 운영 사이트 https://promptdeck.kr/ 의 실제 브라우저 화면 및 DOM 확인.
- 1440×900 데스크톱, 390×844 모바일 화면 확인. 320px 폭에서는 가로 넘침만 추가 확인.
- 메인 상단 ‘작업 도구 열기’를 클릭하여 `/app`의 공통 프롬프트 화면 진입 확인.
- `/`, `/app`, `/guides/`, `/about`, `/features` HTTP 응답 확인.
- 로컬 `static-pages/home.html`, `static-pages/features.html`, `styles/landing.css`, `styles/public-nav.css`, `src/public-nav.js`, 정적 빌드·검증 코드 일부 검토.
- 앱 전체 기능, 모든 링크, 다운로드 파일 무결성, Lighthouse/Core Web Vitals, 전체 키보드·스크린리더 접근성 검사는 이번 범위에 포함하지 않았다.
- 제품 소스 변경·빌드·배포는 수행하지 않았다. 이 문서만 추가했다.

## 3. 운영본과 로컬의 차이

| 항목 | 운영 사이트 | 로컬 소스 |
|---|---|---|
| 기능 소개 | 메인에 11개 메뉴 상세 설명 | 메인은 3개 작업군 요약, 상세는 `/features` |
| 스킬 안내 | 메인에 다운로드 및 설치 방법 | 메인은 짧은 소개, 상세 페이지로 연결 |
| 스타일 예시 | 메인에 3개 이미지 | `/features`로 이동 |
| 상단 메뉴 | 데스크톱 가이드·소개·작업 시작, 모바일 작업 시작 중심 | 기능 드롭다운·스킬 링크·모바일 메뉴 스크립트 포함 |
| `/features` | HTTP 404 | 페이지 및 빌드 대상 존재 |

로컬 변경 방향은 메인 분량을 줄이는 데 적절하다. 다만 운영 반영은 확인되지 않았다. 운영 메인의 기존 기능 버튼은 `/#use-cases`를 가리키므로, `/features` 404를 현재 메인 버튼의 링크 오류로 해석해서는 안 된다. 다음 릴리스에서 HTML·CSS·JS·경로가 함께 반영되는지 확인해야 한다.

## 4. 주요 발견과 개선안

| 우선순위 | 관찰한 내용 | 사용자 영향 | 개선 방향 |
|---|---|---|---|
| P1 | 스타일 이미지에 `width=960`, `height=540`이 있고 CSS는 `width:100%`, `aspect-ratio:16/9`, `object-fit:cover` 적용. 모바일 실측 345×540px | 이미지 좌우가 잘려 레이아웃 비교가 어렵고 페이지가 길어짐 | `height:auto`로 원본 비율 유지. 예시 전체가 보이는지 확인. 로컬에서는 기능 페이지에도 같은 수정 필요 |
| P1 | 운영 페이지 전체 높이 약 8,029px(데스크톱), 14,527px(390px 모바일) | 원하는 도구나 안내를 찾기 위해 긴 스크롤 필요 | 11개 상세 단계와 스킬 설치 절차는 별도 페이지로 이동. 메인은 선택·예시·시작 중심 |
| P1 | 모바일 기능 소개 시작점이 문서 상단 약 1,689px, 실제 스타일 예시 약 7,186px | 사용할 수 있는 기능과 시각적 결과를 늦게 발견 | 히어로 바로 다음에 결과물별 바로가기, 그 다음 간결한 예시 배치 |
| P1 | ‘무료로 작업 시작’은 공통 프롬프트 화면으로 이동 | QR·홍보·라벨 목적의 사용자도 슬라이드 설정부터 접하게 됨 | 일반 CTA와 함께 결과물별 `/app?tab=...` 직접 링크 제공 |
| P1 | 로컬 `/features` 분리 구조와 운영 구조 불일치 | 부분 배포 시 새 경로·내비게이션이 동작하지 않을 가능성 | 정적 빌드와 경로 검증 후 한 번에 릴리스. 배포는 별도 실행 과제 |
| P2 | 히어로의 ‘AI가 그리기 전에, 검토할 수 있게 설계합니다’가 서비스 철학 중심 | 처음 방문한 사람이 구체적으로 무엇을 할 수 있는지 파악하기 어려움 | 첫 제목에 발표자료·홍보 이미지·프롬프트 등 작업을 명시 |
| P2 | ‘정적 공개 기능’, ‘작업 앱은 /app’, ‘도구와 콘텐츠 분리’ 등 구현 설명 노출 | 실제 사용 판단과 관계없는 용어를 읽어야 함 | ‘가입 없이 바로 사용’, ‘작업 화면 광고 없음’ 등 사용자 이점으로 변경. 무료 범위는 기능별 확인 |
| P2 | 원문 보존·검수 원칙을 히어로, 운영 원칙, 4단계, 가이드, 주의사항에서 반복 | 동일 메시지가 반복되어 핵심 기능이 묻힘 | 핵심 원칙은 짧은 안내로 통합, 상세 설명은 가이드·정책에서 제공 |
| P2 | 운영 모바일 상단에는 가이드·소개 탐색 링크가 보이지 않음 | 작업 시작 이외의 탐색은 본문이나 하단에 의존 | 로컬 모바일 메뉴를 검증하여 반영하되 시작 CTA는 쉽게 접근 가능하게 유지 |
| P2 | 로컬 메인 기능 카드도 `/features#...`로만 연결 | 작업을 이미 아는 사용자가 설명 페이지를 한 번 더 거침 | 카드에 ‘바로 시작’과 ‘사용법’ 목적을 구분하여 제공 |
| P2 | 로컬 공통 메뉴 CSS는 모바일에서 JS가 열림 상태를 설정해야 표시됨 | JS 로딩 실패 시 메뉴 접근 저하 가능성 | 기본 HTML 링크는 노출하고 JS 초기화 성공 후에만 접는 방식 검토 |
| P3 | 로컬 CSS의 부드러운 스크롤이 전역 적용 | 움직임 감소 설정에 대응하지 못할 가능성 | `prefers-reduced-motion`에서 자동 스크롤 동작 복원 |

페이지 길이와 위치는 해당 뷰포트·기본 펼침 상태의 관측값이다. 글꼴, 렌더링 환경, 상세 설명 펼침 여부에 따라 달라질 수 있다. 이탈률·전환율에 미치는 영향은 가설이며 실제 사용자 데이터로 검증해야 한다.

## 5. 유지할 요소

- 네이비·블루 중심 색상, 정돈된 카드와 여백, 명확한 주 행동 버튼.
- 프롬프트 구조화 전후를 비교하는 방식. 내용은 더 짧고 구체적으로 개선.
- 가입 화면 없이 작업 앱에 진입할 수 있는 흐름.
- 원문 정보 보존 및 최종 검수 원칙 자체.
- 본문 바로가기, 제목 계층, 이미지 대체 텍스트, canonical·OG·구조화 데이터의 기본 구성.
- 확인한 390px 및 320px 폭에서 문서 전체의 가로 넘침은 없었다.
- 스타일 이미지는 지연 로딩 후 정상 로드되었다. 문제는 파일 누락이 아니라 표시 비율이다.

## 6. 권장 메인 구성

1. **상단 메뉴**: 기능 / 실무 가이드 / 스킬 / 소개 / 작업 시작. 모바일은 메뉴 버튼과 시작 버튼을 함께 제공.
2. **히어로**: 구체적인 효용 한 문장, 보조 설명 두 줄, 시작 버튼과 예시 보기. 프롬프트 예시는 간결하게 유지.
3. **무엇을 만들까요?**: 발표자료, 홍보 이미지, 지도, 데이터 도식, QR, 라벨·티켓의 6개 시작 카드. 사용량 순위가 아니라 작업 범위를 대표하는 초기 편성안이다. 전체 11개 기능 안내 링크 병행.
4. **예시로 확인**: 실제 기능과 연결된 사례 2~3개. 원본 비율 유지. 스타일 참고와 실제 출력 예시를 정확히 구분.
5. **사용 방법**: 내용 입력 → 조건 선택 → 프롬프트 복사·활용. 외부 AI에서 이미지를 만드는 기능과 사이트에서 직접 파일을 만드는 기능의 차이 명시.
6. **가이드·스킬**: 작업을 돕는 보조 콘텐츠로 축약. 설치 상세는 가이드로 연결.
7. **마무리 시작 버튼·운영 정보**: 검수 안내 한 문장과 정책 링크.

히어로 문구 제안:

> 발표자료·홍보 이미지에 쓸 프롬프트를 쉽게 설계하세요.
>
> 내용과 스타일을 정하면 AI에 전달할 작업 지시문을 만듭니다. QR과 라벨은 바로 제작할 수 있습니다.

버튼: **작업 선택하기** / **예시 살펴보기**. 일반 시작 버튼을 `/app`에 연결한다면 도착 화면이 공통 프롬프트라는 사실과 사용 목적을 맞춘다. 선택 영역으로 이동시키는 방식은 새 선택 페이지 없이도 구현 가능하다.

## 7. 실행 순서와 완료 기준

### 1차: 실제 표시 문제와 릴리스 정합성

- 스타일 예시 이미지 높이 수정. 320·390·820·1440px에서 전체 이미지와 캡션 확인.
- 로컬 메인·기능 페이지 분리본 기준 확정. 새 페이지를 중복 개발하지 않고 기존 변경 활용.
- `/features`, 앵커, 메뉴, 앱 직접 링크 및 다운로드 응답 확인.
- 공통 메뉴 변경 시 `node --check src/public-nav.js`, `git diff --check -- index.html src styles`, `node scripts/smoke-test.mjs` 수행. 실패 원인을 분리하여 기록.
- 정적 배포 전 빌드와 `static:test`, `seo:test`, `guides:test`를 변경 범위에 맞춰 수행하고 운영 URL에서 다시 확인.

완료 기준: 이미지 잘림 없음, 새 공개 경로 정상 응답, 데스크톱·모바일 메뉴 접근 가능, JS 실패 시 기본 탐색 유지.

### 2차: 작업 진입 구조 개선

- 히어로 문구 축약, 구현 용어 제거, 결과물별 직접 진입 카드 추가.
- 기능 상세 및 설치 절차를 메인에서 분리하고 원칙 설명 중복 축약.
- 카드별 목적과 도착 탭 일치 확인. 기본 탭만 확인하는 테스트로 대체하지 않음.
- 390×844px에서 주 CTA는 첫 화면에 유지하고 작업 선택 시작을 가능한 한 두 번째 화면 이내에 배치.

완료 기준: 원하는 결과물 카드에서 해당 작업 탭까지 한 번의 클릭으로 이동. 모바일에서 핵심 작업군을 긴 설명보다 먼저 발견.

### 3차: 예시와 성과 검증

- 대표 사례 2~3개와 입력→출력 관계 보강. 출처와 결과물 유형을 정확히 표시.
- 메인 방문→작업 선택→앱 진입→첫 복사·다운로드 완료 흐름을 측정할 이벤트 설계.
- 신규 계측은 개인정보·동의 정책과 기존 분석 구성을 확인한 후 별도 구현.
- 작업 진입률·첫 결과 완료율의 기준값을 수집하고 개선 전후 비교. 현재 데이터가 없으므로 개선율을 단정하지 않음.
- 성능 및 접근성은 Lighthouse와 키보드·실기기 검사로 별도 보강.

## 8. 수정 예상 파일

| 파일 | 역할 |
|---|---|
| `static-pages/home.html` | 히어로, 작업 카드, 콘텐츠 순서·분량 |
| `static-pages/features.html` | 상세 기능, 스타일 예시 및 직접 링크 |
| `styles/landing.css` | 이미지 비율, 모바일 간격, 카드 배치 |
| `styles/public-nav.css`, `src/public-nav.js` | 모바일 탐색, 접근성 및 JS 실패 대응 |
| `scripts/build-static.mjs`, 관련 smoke test | 페이지 출력과 경로·화면 검증 |

실제 패치에서는 기존 변경을 보존하고 부분 수정한다. 커밋·푸시·배포는 이번 점검 및 방향 수립에 포함되지 않는다.
